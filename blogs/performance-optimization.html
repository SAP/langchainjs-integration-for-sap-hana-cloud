Performance Optimization with SAP HANA Cloud and LangChain.js

Your prototype works. You loaded a few hundred documents into HanaDB, ran a similarity search, demoed it to your team, got the green light. Now product wants to load 25,400 research papers by next week, and search latency needs to stay under a second.

This is the scale where the difference between a toy and a product gets decided. @sap/hana-langchain ships three optimisations that tilt the math in your favour: Map Merge for bulk inserts, HNSW indexes for fast search at scale, and specific metadata columns for fast filtering. We benchmarked all three on a real arXiv dataset. The numbers are striking.

Full walkthrough on GitHub: blogs/performance-optimization.md. Every code sample, every benchmark script, every parameter table.

The dataset: 25,400 arXiv abstracts

To make these numbers concrete and reproducible, the benchmarks below all use a real corpus: 25,400 arXiv research paper abstracts drawn from the gfissore/arxiv-abstracts-2021 dataset on Hugging Face. Average abstract is about 1 KB. Embeddings are computed by HANA itself via HanaInternalEmbeddings.

Note: All measurements in this guide were taken on a server machine with 48 cores. Absolute numbers will vary with your hardware, SAP HANA Cloud configuration, network latency, and document size, so treat them as relative comparisons rather than fixed figures.

Bulk inserts: 8.7× faster with Map Merge

The default addDocuments path is sequential. Embed a document, insert a row, repeat. Fine for hundreds of records, painful at 25,000. Map Merge uses HANA’s MAP_MERGE primitive to embed and insert in parallel across database nodes, with columnar batching and minimal client-server chatter.

One flag turns it on:

// Default behavior: sequential, simple, slow at scale
await vsStandard.addDocuments(documents);

// Parallel, columnar, dramatically faster
await vsMapMerge.addDocuments(documents, { useMapMerge: true });

And here’s what that flag bought us on 25,400 abstracts:

Map Merge: 354.2s   (~6 minutes,   72 docs/s)
Standard:  3087.3s  (~51 minutes,   8 docs/s)
Speedup:   8.7x faster with Map Merge

That’s a coffee break versus a long lunch. And it scales: the more documents you have, the more the parallelism wins.

The catch: Map Merge requires HanaInternalEmbeddings. External embedding APIs can’t be parallelised inside the database, so they’re not supported here. The good news: HanaInternalEmbeddings is faster, cheaper, and more private anyway.

Fast search at scale: HNSW indexes

By default, similarity search in HanaDB is exact. It computes the distance from your query to every single vector in the table and picks the closest. Beautiful at small scale, brutal at large scale.

HNSW (Hierarchical Navigable Small World) trades a tiny amount of recall for sub-linear search time. It builds a multi-layer graph where higher layers act like an express train and lower layers handle precise neighbour lookups. Once it’s built, your queries don’t care how big your dataset gets.

Building the index is one line:

// Default settings, sensible for most workloads
await vectorStore.createHnswIndex();

// Or tune for your specific recall/latency target
await vectorStore.createHnswIndex({
  m: 64,                  // max neighbours per node (memory vs. quality)
  efConstruction: 200,    // build-time accuracy
  efSearch: 400,          // query-time accuracy
});

Once it’s built, every similaritySearch call automatically uses it. No code changes downstream.

So when does HNSW pay off?

Here’s the honest answer, and it surprises people:

Search without HNSW: 72ms
HNSW index created in 1522ms
Search with HNSW:    105ms

At 25,400 documents, exact search is actually faster. The graph-traversal overhead of HNSW outweighs its asymptotic advantage at this size. But scale up and the curves cross dramatically:

Dataset Size    Exact Search    HNSW Search    Recommendation
   25K               ~72ms          ~105ms       Use exact search
  100K              ~183ms          ~140ms       HNSW recommended
  500K              ~991ms          ~166ms       HNSW essential
   1M+                ~2s+          ~200ms       HNSW required

HNSW search time remains relatively stable (~100-200ms) regardless of dataset size, while exact search scales linearly.

Faster filtering: specific metadata columns

By default, HanaDB stores all metadata as JSON in a single column. That’s perfectly fine, until you start filtering on the same field over and over. Each filtered query parses the JSON, every time.

For frequently filtered fields, you can promote them into dedicated SQL columns. Native column comparisons replace JSON parsing, and the database can index them properly.

Create the table with the columns you care about:

CREATE TABLE "PAPERS_SPECIFIC_COLUMNS" (
  "VEC_TEXT" NCLOB,
  "VEC_META" NCLOB,
  "VEC_VECTOR" REAL_VECTOR,
  "primaryCategory" NVARCHAR(100),
  "id" NVARCHAR(100)
);

Then point HanaDB at them:

const vsColumns = new HanaDB(embeddings, {
  connection: client,
  tableName: "PAPERS_SPECIFIC_COLUMNS",
  specificMetadataColumns: ["primaryCategory", "id"],
});

The library quietly steers anything mentioning primaryCategory or id in your filter into native SQL comparisons; everything else still uses the JSON column. Same filter syntax, no client-side change.

Filtering 25,400 papers by primaryCategory:

JSON metadata filtering:    166ms
Specific columns filtering: 126ms
Speedup: 1.3x faster with specific columns

Modest at this scale, because HANA’s JSON parser is already very fast. The gap widens as your dataset grows and as your filter conditions get more complex. The win is most pronounced for exact-match filters (categories, statuses, IDs) and range filters (prices, dates).

The production playbook

  1. Use HanaInternalEmbeddings. Required for Map Merge, lower latency, no external API costs.
  2. Bulk-load with Map Merge. Whenever you’re inserting more than a few hundred documents at once.
  3. Build the HNSW index after your initial load. Indexing during streaming inserts wastes work. One createHnswIndex() call when the data is settled.
  4. Promote your hot filter fields to specific columns. Pick the one to three fields you filter on most. Don’t over-do it; sparse JSON metadata is fine for the rest.
  5. Tune to your recall target. Higher efSearch = better recall, slower queries. Higher m = better quality, more memory. Profile, then pick.
