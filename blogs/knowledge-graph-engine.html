Knowledge Graphs with SAP HANA Cloud and LangChain.js

Vector search is brilliant when your question is fuzzy. But some questions aren’t fuzzy at all. They’re structural.

“Which countries had treaties with both the USA and the USSR during the Cold War?”

That’s not a similarity question. That’s a graph question. And SAP HANA Cloud’s Knowledge Graph Engine answers it in milliseconds, natively, with SPARQL, directly inside the database where your data already lives.

With @sap/hana-langchain’s HanaRdfGraph, you can connect to that engine in two lines and start asking questions about relationships, not just text.

Full walkthrough on GitHub: blogs/knowledge-graph-engine.md. Every code sample, every query, and every output.

Two lines, one knowledge graph

Once your HANA Cloud instance has the triplestore feature enabled (ask your admin), connecting is a one-liner: 

import { HanaRdfGraph } from "@sap/hana-langchain";

const graph = new HanaRdfGraph({
  connection: client,
  graphUri: "http://company.example.com/org-chart",
  autoExtractOntology: true, // infer the schema from the data
});
await graph.initialize(graphOptions);

That autoExtractOntology: true flag is the magic dust for prototyping. It walks your data, figures out the classes and predicates, and hands you a working schema. No .ttl file, no manual modeling. When you’re ready to harden things up, swap it for an explicit ontology file or a custom CONSTRUCT query.

The Cold-War dataset, in 2,024 triples

Let’s make this concrete with a real dataset: the open-source nations dataset, 2,024 triples describing the diplomatic web between fourteen nations during the Cold War era. Treaties. Economic aid. Embassies. Military alliances. Trade.

Loading it into HANA is a single SPARQL INSERT:

Loaded 2024 triples into Nations graph

Now we can ask the database questions that simply cannot be expressed as a SQL WHERE clause.

Question one: who had treaties with the USA?

const usaTreaties = await graph.query(`
  SELECT ?country
  WHERE {
    ?country <treaties> <USA> .
  }
  ORDER BY ?country
`);

Question two: who’s receiving aid from multiple donors?

Now things get interesting. Try doing this with joins:

const multiAid = await graph.query(`
  SELECT ?recipient (COUNT(?donor) AS ?donorCount)
  WHERE {
    ?donor <economicaid> ?recipient .
  }
  GROUP BY ?recipient
  HAVING (COUNT(?donor) > 1)
  ORDER BY DESC(?donorCount)
`);

recipient,donorCount
India,3
Egypt,2
Jordan,2

India is being funded by three different superpowers. Egypt and Jordan by two. The dataset has just told us the geopolitical hot zones, and the SPARQL reads almost like the English question.

Question three: who has mutual treaties?

This is where graphs really earn their keep. A bilateral relationship means “A has a treaty with B and B has a treaty with A”: a graph cycle of length two. In SQL, painful. In SPARQL, the pattern is the query: 

const bilateral = await graph.query(`
  SELECT DISTINCT ?country1 ?country2
  WHERE {
    ?country1 <treaties> ?country2 .
    ?country2 <treaties> ?country1 .
    FILTER (STR(?country1) < STR(?country2))
  }
  ORDER BY ?country1 ?country2
`);

Yes, even at the height of the Cold War, the USA and USSR had bilateral treaties. The graph knows.

One graph, four ways to load its schema

Different teams, different workflows. HanaRdfGraph supports four ontology-loading strategies so you can match your data-management style:

  • Auto-extract: fastest path, perfect for prototyping or when the schema is implicit in your triples.
  • Separate graph: point ontologyUri at a named graph that holds your owl:Class and rdfs:Property definitions.
  • Local Turtle file: keep your ontology in version control alongside your code (./ontologies/product-schema.ttl).
  • Custom CONSTRUCT query: surgical control over exactly which schema elements get extracted.

Start with auto-extract; promote to a hand-curated ontology when production calls for it. Same code, different config.

Where this gets really powerful

Knowledge graphs alone are excellent. Knowledge graphs combined with vector search are next-level. Imagine a customer-success app where the graph tells you which customers placed more than 100 orders, and the vector store tells you what they’re currently complaining about: 

// Semantic side: what are they saying?
const complaints = await vectorStore.similaritySearch(
  "customer complaints about delivery",
  5,
);

// Structural side: who are the high-value customers?
const vips = await graph.query(`
  SELECT ?customer ?orderCount WHERE {
    ?customer a :Customer ;
              :totalOrders ?orderCount .
    FILTER (?orderCount > 100)
  }
`);

// Join the two sides in your application and you have a feature
// that no single retrieval technique could deliver.

That intersection of fuzzy intent plus hard structural facts is where the real product magic happens. Both stores live inside the same HANA Cloud instance, so there’s no second database to operate, no ETL pipeline to maintain, no consistency drift.

The cheat sheet

  • Document your ontology like you’d document an API. rdfs:label and rdfs:comment aren’t just for humans; they’re the prompt context an LLM uses to write good SPARQL.
  • Auto-extract for prototypes, explicit ontology for production. Move from autoExtractOntology: true to a curated .ttl as your data model stabilises.
  • Lean on HANA’s SPARQL endpoint. Aggregations, path queries, and graph traversals all run inside the database. No application-side joins, no round-trips per hop.
  • Combine with HanaDB. Structural questions and semantic questions are usually two halves of the same answer. Use both.
