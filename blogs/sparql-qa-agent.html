Natural Language Queries on Knowledge Graphs with SAP HANA Cloud and LangChain.js

Your knowledge graph contains exactly the answer. The problem is getting it out.

“Which scientists have won more than one Nobel Prize?”

Answering that question by hand means knowing the exact class URIs, the predicate names, the right prefixes, and where the graph lives. It means writing SPARQL. Most developers don’t want to do that for every question a user might ask — and they shouldn’t have to.

That’s the problem HanaSparqlQAAgent solves. Give it a plain English question. It reads the ontology, writes the SPARQL, runs it against your SAP HANA Cloud triple store, and hands back a natural-language answer. The query language stays invisible.

Full walkthrough on GitHub: blogs/sparql-qa-agent.md. Complete code, setup instructions, and customization options.

The two tools that make it work

The agent doesn’t guess. It reasons step by step using exactly two built-in tools: 

User Question
      │
      ▼
┌─────────────────────┐
│  retrieveOntology   │  Returns the graph's OWL schema in Turtle format
│  (tool call 1)      │  Agent learns available classes and properties
└─────────────────────┘
      │
      ▼
┌─────────────────────┐
│  executeSparql      │  Runs the generated SELECT query against HANA
│  (tool call 2)      │  Returns raw query results
└─────────────────────┘
      │
      ▼
Natural language answer synthesized from results

Step one is always to retrieve the ontology. The agent can’t write correct SPARQL without knowing what class URIs and predicates exist — so it asks first, rather than guessing. Against the Nobel Prize graph, it learns about the nobel:Laureate, nobel:NobelPrize, and nobel:LaureateAward classes, along with properties like foaf:name, nobel:year, nobel:category, and dbo:birthPlace.

Step two is execution. The agent writes a SELECT query grounded strictly in the ontology it just read, and executeSparql runs it. The tool automatically injects the correct FROM clause so the query always targets the right named graph — no manual plumbing required.

The built-in system prompt enforces a hard constraint: only SELECT queries. No INSERT, UPDATE, or DELETE can be generated. The safest complement to that is using a read-only database user, which the best-practices section covers below.

Getting started in ten lines

The Nobel Prize Foundation publishes their full dataset as RDF Linked Data at data.nobelprize.org, accessible through a public SPARQL endpoint. You can dump the entire graph with one query — the endpoint returns CSV, so pass Accept: text/csv: 

curl -G "https://data.nobelprize.org/store/sparql" \
  --data-urlencode "query=SELECT DISTINCT ?s ?p ?o WHERE { ?s ?p ?o }" \
  -H "Accept: text/csv" \
  -o nobel_prizes.csv

SELECT DISTINCT is necessary because the platform stores each triple in two named graphs — without it every triple appears twice.

Before inserting into HANA, filter out two categories of triples:

  • Blank nodes — triples whose subject or object is an anonymous blank node (_:b0). Blank nodes have no stable URI and cannot be matched in subsequent queries.
  • Invalid xsd:date literals — the dataset uses partial dates like "1956-00-00"^^xsd:date for laureates with unknown birth dates. HANA rejects month or day values of 00.

Then insert the filtered triples into a named graph using INSERT DATA via SYS.SPARQL_EXECUTE. For large datasets, split the triples across multiple statements rather than sending them all at once: 

await new Promise<void>((resolve, reject) => {
  client.prepare("CALL SYS.SPARQL_EXECUTE(?, ?, ?, ?)", (err, stmt) => {
    if (err) return reject(err);
    stmt.exec(
      { REQUEST: `INSERT DATA { GRAPH <nobelprizes> { ${triples} } }`, PARAMETER: "" },
      (err2: Error) => (err2 ? reject(err2) : resolve())
    );
  });
});

With the data in HANA, connect and initialize the graph:

import hanaClient from "@sap/hana-client";
import { AzureOpenAiChatClient } from "@sap-ai-sdk/langchain";
import {
  HanaRdfGraph,
  HanaSparqlQAAgent,
} from "@sap/hana-langchain";

const client = hanaClient.createConnection({
  host: process.env.HANA_DB_ADDRESS,
  port: process.env.HANA_DB_PORT,
  user: process.env.HANA_DB_USER,
  password: process.env.HANA_DB_PASSWORD,
});
await new Promise<void>((resolve, reject) => {
  client.connect((err: Error) => (err ? reject(err) : resolve()));
});

const graph = new HanaRdfGraph({
  connection: client,
  graphUri: "nobelprizes",
  autoExtractOntology: true,
});
await graph.initialize({
  connection: client,
  graphUri: "nobelprizes",
  autoExtractOntology: true,
});

const agent = HanaSparqlQAAgent.createAgent(
  new AzureOpenAiChatClient({ modelName: "gpt-4o" }),
  { graph }
);

const result = await agent.invoke({
  messages: [{ role: "user", content: "Who won the Nobel Prize in Literature in 1947?" }],
});
console.log(result.messages.at(-1)?.content);

André Gide won the Nobel Prize in Literature in 1947, for his comprehensive
and artistically significant writings, in which human problems and conditions
have been presented with a fearless love of truth and keen psychological insight.

autoExtractOntology: true runs a built-in CONSTRUCT query that derives an OWL schema directly from your data. No separate ontology file needed to get started. For large or complex graphs, you can supply a custom CONSTRUCT query, a remote ontology URI, or a local RDF file instead — the full options table is in the companion guide.

Note: LLM outputs are non-deterministic — the exact SPARQL generated and the phrasing of answers will vary between runs. More capable models generally produce more accurate queries and more reliable answers.

What the agent can answer

Simple lookups, multi-hop traversal, and aggregation queries all work out of the box. Ask about a specific year: 

Q: Who won the Nobel Prize in Physics in 2018?

The Nobel Prize in Physics 2018 was awarded to three scientists:
- Arthur Ashkin (Bell Laboratories, USA)
- Gérard Mourou (École Polytechnique, France / University of Michigan, USA)
- Donna Strickland (University of Waterloo, Canada)

Ask a biographical question that requires following relationships across nodes — from laureate to birthplace to country: 

Q: In which city was Marie Curie born, and how many Nobel Prizes did she win?

Marie Curie was born in Warsaw, Poland. She won two Nobel Prizes:
the Nobel Prize in Physics in 1903 and the Nobel Prize in Chemistry in 1911,
making her the first person to win Nobel Prizes in two different sciences.

Ask for aggregations that the agent turns into GROUP BY queries:

Q: Which university has produced the most Nobel laureates?

The University of California has produced the most Nobel laureates,
with 42 laureates affiliated with the university.

And when the data genuinely isn’t there, the agent says so honestly rather than hallucinating: 

Q: Who won the Nobel Prize in Artificial Intelligence?

There is no Nobel Prize in Artificial Intelligence in the available data.
The Nobel Prize categories are Physics, Chemistry, Physiology or Medicine,
Literature, Peace, and Economic Sciences.

Streaming for interactive apps

For a UI that starts displaying results before the full answer is ready, swap invoke for stream: 

for await (const [chunk] of await agent.stream(
  { messages: [{ role: "user", content: "Which scientists have won more than one Nobel Prize?" }] },
  { streamMode: "messages" }
)) {
  if (chunk.content) process.stdout.write(chunk.text);
}

Several scientists have won more than one Nobel Prize:

- Marie Curie — Physics (1903) and Chemistry (1911)
- John Bardeen — Physics (1956) and Physics (1972)
- Linus Pauling — Chemistry (1954) and Peace (1962)
- Frederick Sanger — Chemistry (1958) and Chemistry (1980)
- K. Barry Sharpless — Chemistry (2001) and Chemistry (2022)

The International Committee of the Red Cross has received three Nobel Peace Prizes
(1917, 1944, and 1963).

The interface is identical to every other LangChain agent — if you’ve streamed a chat model before, you already know how this works.

Extending the agent

The defaults cover the common case, but the agent is designed to be extended. Three common patterns:

Extra tools. Pass additional tools in HanaSparqlQAAgentOptions.tools and they sit alongside the built-in pair. Useful for date lookups, external API calls, or domain-specific calculations the LLM might need alongside graph results.

Custom system prompt. Override systemPrompt to specialize the agent for a domain, add persona constraints, or restrict the kinds of questions it will answer. The built-in prompt is still a useful starting point to extend rather than replace entirely.

Full control. Set includeDefaultTools: false and includeDefaultMiddleware: false to supply your own tool set and retry logic from scratch — useful when you need a tightly controlled production agent with custom rate-limiting or observability hooks.

The cheat sheet

  • Use read-only credentials. The prompt forbids write queries, but a read-only database user is the defense-in-depth layer that makes it impossible for a prompt injection to do damage.
  • Inspect the schema before deploying. Call graph.getSchema() and serialize it to Turtle. If the ontology looks sparse, switch from autoExtractOntology to a custom ontologyQuery that covers the full structure.
  • Add rdfs:label to everything. The system prompt instructs the agent to retrieve labels when they exist. Answers built from human-readable names are far more useful than answers built from raw URIs.
  • Custom CONSTRUCT for complex graphs. autoExtractOntology does a best-effort schema inference from the data. A hand-written CONSTRUCT query from a separate ontology graph gives the agent a more precise and complete picture.
